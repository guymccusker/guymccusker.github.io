# guymccusker.github.io — build notes

Site sources live as org-mode files under `content/`. `publish.el` uses
Emacs's built-in `org-publish` (no ox-hugo, no external exporter) to turn
them into static HTML under `public/`, which is what actually gets
deployed to GitHub Pages.

## Layout

```
content/            org-mode source: index.org, publications.org, ...
content/inc/         fragments pulled into other pages via #+INCLUDE
content/talks -> ../talks   symlink, for local link navigation only (see below)
assets/css/          site stylesheet (style.css)
assets/img/          images
talks/               existing reveal.js talk decks — copied through as-is
scripts/fetch_publications.py   pulls the Bath Research Portal RSS feed
publish.el           org-publish-project-alist + preamble/postamble
.github/workflows/build.yml     CI: refresh publications, build, deploy
public/              build output (gitignored, not committed)
```

### Links inside `content/inc/*.org` fragments

`#+INCLUDE` isn't a dumb text splice — org rewrites relative `file:` links
in the included content by prepending the fragment's own directory
relative to the includer before export. So a fragment one level down in
`inc/` needs exactly one `../` on any link that should resolve the same
way it would if written directly in `index.org` (two levels down would
need `../../`, etc.). That's why `content/inc/talks.org` and
`content/inc/news.org` link to `../talks/...` and `../publications.org`
rather than the paths you'd expect from `inc/`'s real position in the
source tree.

That mismatch broke `C-c C-o` / org-open-at-point navigation while
editing those fragments locally, since `../talks/...` from `content/inc/`
naively resolves to `content/talks/...`, which doesn't exist. Fixed with
`content/talks`, a symlink to `../talks` (the real top-level talks
directory) — it makes the export-correct path also resolve to a real
file on disk when editing locally, with no change to the link text
itself. It's a navigation convenience only; org-publish never descends
into it (`site-pages` runs non-recursively), and the actual `talks/`
build output still comes from the top-level `talks/` directory via the
separate `site-talks` project.

## Building locally

You'll need Emacs with a reasonably recent org-mode (9.5+, which ships
with Emacs 27+). From the repo root:

```sh
emacs --batch -l publish.el --eval '(org-publish "site" t)'
```

The `t` forces a full rebuild; drop it for an incremental one. Output
lands in `public/`; open `public/index.html` in a browser to check it.

To refresh the publications list from the Research Portal before
building:

```sh
pip install beautifulsoup4
python3 scripts/fetch_publications.py \
  --feed-url "https://researchportal.bath.ac.uk/en/persons/guy-mccusker/publications/?format=rss" \
  --out content/publications.org
```

`content/publications.org` is checked in as a starting point (generated
from a sample of the feed) but is meant to be regenerated by this script
— treat it as build output, not something to hand-edit.

## What I couldn't verify myself

I don't have Emacs available in my sandbox (no root access to install
it), so `publish.el` and the CSS have not been run through the real
`org-html-publish-to-html` exporter — only checked by hand against how
org's HTML export is documented to behave (heading levels, the
`outline-N` / `HTML_CONTAINER_CLASS` wrapping, etc.) and previewed with a
hand-built approximation. Please run the build locally and tell me what
breaks — heading levels or container classes being off is the most
likely source of any CSS mismatches.

## Known open items

- `content/publications.org` currently lists every record from the
  portal, including cases where the same paper has multiple entries
  (e.g. a conference version and a later journal version). That's
  normal for a Pure/CRIS feed, not a bug, but let me know if you'd
  rather they were deduplicated or merged.
- The other legacy pages (`projects.html`, `sci.html`, teaching
  materials, `extensional.html`, `hybrid.html`) haven't been migrated
  into org yet — only the homepage and publications, per what we'd
  agreed to build first.
- Email address is obfuscated with numeric HTML character references
  rather than JavaScript. It's a mild deterrent, not a strong one — happy
  to swap in a different approach if you'd prefer.
